  <name>Task 3: TBA two-ping 48h re-audit loop — Ping #1 and Ping #2</name>
  <files>packages/orchestrator/src/tba-loop.ts, packages/orchestrator/src/orchestrator.ts</files>
  <action>
    Implement the TBA re-audit loop that scans deadlines.tba=true rows, re-audits them every 48h, and fires Ping #1 (TBA detected) and Ping #2 (confirmed or expired).

    **per D-10** — TBA re-audit reuses the existing audit-drain (every 5m + 60s jitter): scan deadlines.tba=true rows whose last audit was >48h ago, re-audit them, until the event date/time arrives. Ping #1 fires when TBA detected (routes to #⏳-early-tba-radar with WATCHING_TBA status). Ping #2 fires when prize/date is confirmed or event passes. No new scheduler job needed.

    **Implementation steps:**

    1. **`packages/orchestrator/src/tba-loop.ts`** — Create the TBA re-audit module:
       - Export `tbaReauditScan(opts: { pb: PbLike; router: LlmRouter; log?: Logger; client?: any; env?: Env }): Promise<void>`.
       - Scan `opportunities` collection: `filter: "deadlines.tba = true && updated < '${fortyEightHoursAgo}'"`, `sort: 'updated'`, page size 50.
       - For each TBA row:
         a. Re-run the audit pipeline on the opportunity's `partial_buffer` (reuse the appropriate rule pack — events rule pack for events pipeline, local rule pack for local pipeline).
         b. Parse the new verdict. If prize/date now confirmed (verdict has non-null prize_cash_inr or dates):
            - **Ping #2 (confirmed):** Update the opportunity: `deadlines.tba: false`, `status: 'audited'`, update `prize_cash_inr`, `prize_text`, `deadlines` from the new verdict. Route to #⏳-early-tba-radar if not already there, or update the existing post.
            - Set `tba: false` to terminate the loop.
         c. If event date has passed (verdict dates are in the past):
            - **Ping #2 (expired):** Update the opportunity: `deadlines.tba: false`, `status: 'expired'`. Tombstone as `event_expired`.
            - Set `tba: false` to terminate the loop.
         d. If still TBA (prize/date still unknown after re-audit):
            - Keep `deadlines.tba: true`, update `updated` timestamp so the next scan is 48h later.
            - Do NOT re-ping — Ping #1 already fired when TBA was first detected.
       - Handle errors per-row (never abort the batch).

    2. **`packages/orchestrator/src/orchestrator.ts`** — Wire TBA scan into the audit-drain tick:
       - In `drainStep2Rows` (or in the audit-drain tick handler that calls it), after processing STEP_2 rows, call `tbaReauditScan` with the same pb, router, and log.
       - The TBA scan runs within the existing audit-drain cron job (every 5m + 60s jitter) — no new scheduler job (per D-10).
       - **Ping #1** fires when TBA is first detected: this happens in `processEventsRow` and `drainLocalRow` when the verdict has null prize_cash_inr or dates. Set `deadlines.tba: true`, route to `#⏳-early-tba-radar` with `status: 'audited'`, and log "Ping #1: TBA detected".

    **Terminal conditions (per Pitfall 4):**
    - Prize/date confirmed → tba=false, Ping #2 fired
    - Event date passed → tba=false, status=expired, Ping #2 fired
    - The loop MUST terminate on either condition — TBA rows must not accumulate forever.

    **Do NOT:**
    - Do NOT create a new scheduler job for TBA — D-10 explicitly reuses the existing audit-drain.
    - Do NOT fire Ping #1 more than once per opportunity — Ping #1 fires only when TBA is first detected.
    - Do NOT leave TBA rows in an infinite loop — terminal conditions must always fire.
  </action>
